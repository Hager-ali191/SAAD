## Project Planning Overview
* Project planning involves breaking down the work into parts and assigning these to project team members.[cite: 3]
* Planning requires anticipating problems that might arise and preparing tentative solutions to those problems.[cite: 3]
* The project plan is created at the start of a project.[cite: 3]
* The plan is used to communicate how the work will be done to the project team and customers, and to help assess progress on the project.[cite: 3]

## Planning Stages

| Stage | Description |
| :--- | :--- |
| **Proposal planning**[cite: 3] | Occurs at the proposal stage when bidding for a contract to develop or provide a software system.[cite: 3] Planning may be necessary with only outline software requirements.[cite: 3] The aim is to provide information used in setting a price for the system to customers.[cite: 3] |
| **Project startup planning**[cite: 3] | Occurs during the project startup phase.[cite: 3] You know more about system requirements but do not have design or implementation information.[cite: 3] Used to plan who will work on the project, how it will be broken down into increments, and resource allocation.[cite: 3] Creates a plan with enough detail for budget and staffing decisions.[cite: 3] Defines project monitoring mechanisms.[cite: 3] A startup plan is also needed for agile development to allocate resources.[cite: 3] |
| **Development planning**[cite: 3] | Occurs periodically throughout the project.[cite: 3] The project plan should be regularly amended as the project progresses, modifying it in light of experience gained and progress monitoring.[cite: 3] The project schedule, cost-estimate, and risks have to be regularly revised.[cite: 3] |

## Software Pricing
* Estimates are made to discover the cost, to the developer, of producing a software system.[cite: 3]
* You take into account hardware, software, travel, training, and effort costs.[cite: 3]
* There is not a simple relationship between the development cost and the price charged to the customer.[cite: 3]
* Broader organizational, economic, political, and business considerations influence the price charged.[cite: 3]

### Pricing Strategies

| Strategy | Description |
| :--- | :--- |
| **Under pricing**[cite: 3] | A company may underprice a system to gain a contract that allows them to retain staff for future opportunities.[cite: 3] A company may also underprice to gain access to a new market area.[cite: 3] |
| **Increased pricing**[cite: 3] | The price may be increased when a buyer wishes for a fixed-price contract, allowing the seller to increase the price to account for unexpected risks.[cite: 3] |

### Factors Affecting Software Pricing

| Factor | Description |
| :--- | :--- |
| **Contractual terms**[cite: 3] | A customer may allow the developer to retain ownership of the source code and reuse it in other projects.[cite: 3] The price charged may then be less than if the source code is handed over to the customer.[cite: 3] |
| **Cost estimate uncertainty**[cite: 3] | If an organization is unsure of its cost estimate, it may increase its price by a contingency over and above its normal profit.[cite: 3] |
| **Financial health**[cite: 3] | Developers in financial difficulty may lower their price to gain a contract.[cite: 3] It is better to make a smaller than normal profit or break even than to go out of business.[cite: 3] Cash flow is more important than profit in difficult economic times.[cite: 3] |
| **Market opportunity**[cite: 3] | A development organization may quote a low price to move into a new segment of the software market.[cite: 3] Accepting a low profit on one project may give the organization the opportunity to make a greater profit later.[cite: 3] The experience gained may also help it develop new products.[cite: 3] |
| **Requirements volatility**[cite: 3] | If requirements are likely to change, an organization may lower its price to win a contract.[cite: 3] After the contract is awarded, high prices can be charged for changes to the requirements.[cite: 3] |

## Plan-Driven Development
* Plan-driven development is an approach where the development process is planned in detail.[cite: 3]
* It is the "traditional" way of managing large software development projects.[cite: 3]
* A project plan is created that records the work to be done, who will do it, the development schedule, and the work products.[cite: 3]
* Managers use the plan to support project decision making and to measure progress.[cite: 3]

### Pros and Cons of Plan-Driven Development

| Aspect | Description |
| :--- | :--- |
| **Arguments in favor (Pros)**[cite: 3] | Early planning allows organizational issues (availability of staff, other projects) to be closely taken into account.[cite: 3] Potential problems and dependencies are discovered before the project starts, rather than once it is underway.[cite: 3] |
| **Principal argument against (Cons)**[cite: 3] | Many early decisions have to be revised because of changes to the environment in which the software is to be developed and used.[cite: 3] |

## Project Plans
* In a plan-driven project, a project plan sets out the resources available to the project, the work breakdown, and a schedule for carrying out the work.[cite: 3]
* **Plan sections:** Introduction, Project organization, Risk analysis, Hardware and software resource requirements, Work breakdown, Project schedule, Monitoring and reporting mechanisms.[cite: 3]

### Project Plan Supplements

| Plan | Description |
| :--- | :--- |
| **Configuration management plan**[cite: 3] | Describes the configuration management procedures and structures to be used.[cite: 3] |
| **Deployment plan**[cite: 3] | Describes how the software and associated hardware (if any) will be deployed in the customer's environment.[cite: 3] This should include a plan for migrating data from existing systems.[cite: 3] |
| **Maintenance plan**[cite: 3] | Predicts the maintenance requirements, costs, and effort.[cite: 3] |
| **Quality plan**[cite: 3] | Describes the quality procedures and standards that will be used in a project.[cite: 3] |
| **Validation plan**[cite: 3] | Describes the approach, resources, and schedule used for system validation.[cite: 3] |

## The Planning Process
* Project planning is an iterative process starting when an initial project plan is created during project startup.[cite: 3]
* Plan changes are inevitable.[cite: 3]
* The plan should be regularly revised to reflect requirements, schedule, and risk changes as more information becomes available.[cite: 3]
* Changing business goals also lead to changes in project plans, potentially affecting all projects which may then have to be re-planned.[cite: 3]

### The Project Planning Process Flow

| Step | Action | Next Condition / Path |
| :--- | :--- | :--- |
| **1**[cite: 3] | Identify constraints, identify risks, and define milestones and deliverables.[cite: 3] | Proceed to define project schedule.[cite: 3] |
| **2**[cite: 3] | Define project schedule.[cite: 3] | Proceed to do the work.[cite: 3] |
| **3**[cite: 3] | Do the work.[cite: 3] | If unfinished, loop back to doing work.[cite: 3] If finished, the project completes.[cite: 3] |
| **4**[cite: 3] | Monitor progress against plan.[cite: 3] | **If no problems:** Continue doing work.[cite: 3] <br> **If minor problems and slippages:** Loop back to redefine project schedule.[cite: 3] <br> **If serious problems:** Initiate risk mitigation actions and replan project.[cite: 3] |

### Planning Assumptions & Risk Mitigation
* You should make realistic rather than optimistic assumptions when defining a plan.[cite: 3]
* Problems always arise and lead to delays.[cite: 3] Initial assumptions and scheduling should take unexpected problems into account.[cite: 3]
* You should include contingency in your plan so your delivery schedule is not seriously interrupted if things go wrong.[cite: 3]
* If there are serious problems likely to lead to significant delays, initiate risk mitigation actions to reduce the risks of project failure.[cite: 3]
* In conjunction with these actions, you have to re-plan the project.[cite: 3]
* This may involve renegotiating constraints and deliverables with the customer, and establishing a new schedule agreed upon with the customer.[cite: 3]

## Project Scheduling
* Project scheduling is the process of deciding how the work will be organized as separate tasks, and when and how these tasks will be executed.[cite: 3]
* You estimate the calendar time needed, effort required, and who will work on the tasks.[cite: 3]
* You estimate the resources needed to complete each task (e.g., server disk space, specialized hardware time like a simulator, and travel budget).[cite: 3]

### Project Scheduling Activities
* Split the project into tasks and estimate the time and resources required to complete each task.[cite: 3]
* Organize tasks concurrently to make optimal use of the workforce.[cite: 3]
* Minimize task dependencies to avoid delays caused by one task waiting for another to complete.[cite: 3]
* Dependent on project managers' intuition and experience.[cite: 3]

### The Project Scheduling Process Flow

| Order | Activity | Input / Output |
| :--- | :--- | :--- |
| **1**[cite: 3] | Identify activities[cite: 3] | **Input:** Software requirements and design information[cite: 3] |
| **2**[cite: 3] | Identify activity dependencies[cite: 3] | Proceeds to estimating resources[cite: 3] |
| **3**[cite: 3] | Estimate resources for activities[cite: 3] | Iterative loop with allocating people[cite: 3] |
| **4**[cite: 3] | Allocate people to activities[cite: 3] | Iterative loop back to estimating resources[cite: 3] |
| **5**[cite: 3] | Create project charts[cite: 3] | **Output:** Bar charts describing the project schedule[cite: 3] |

### Scheduling Problems
* Estimating the difficulty of problems and the cost of developing a solution is hard.[cite: 3]
* Productivity is not proportional to the number of people working on a task.[cite: 3]
* Adding people to a late project makes it later because of communication overheads.[cite: 3]
* The unexpected always happens; always allow contingency in planning.[cite: 3]

## Schedule Presentation & Project Activities
* Graphical notations are normally used to illustrate the project schedule, showing the project breakdown into tasks.[cite: 3]
* Tasks should not be too small; they should take about a week or two.[cite: 3]
* **Calendar-based (Bar charts):** Most commonly used representation; show the schedule as activities or resources against time.[cite: 3]
* **Activity networks:** Show task dependencies.[cite: 3]
* **Project activities (tasks) features:**
  * A duration in calendar days or months.[cite: 3]
  * An effort estimate (number of person-days to complete the work).[cite: 3]
  * A deadline by which the activity should be complete.[cite: 3]
  * A defined end-point (e.g., a document, review meeting, successful test execution).[cite: 3]

### Milestones and Deliverables
* **Milestones:** Points in the schedule against which you can assess progress (e.g., handover of the system for testing).[cite: 3]
* **Deliverables:** Work products that are delivered to the customer (e.g., a requirements document).[cite: 3]
* You should use a project planning tool (e.g., Basecamp or Microsoft Project) to create, update, and analyze project schedule information.[cite: 3]
* These tools expect input into a table, create a database of project information, and automatically generate bar charts and activity charts.[cite: 3]

## Activity Network Diagram
* It is a diagram of project activities that shows the sequential relationships of activities using arrows and nodes.[cite: 3]
* An activity network diagram tool is necessary for the identification of a project's critical path, which is used to determine the expected completion time of the project.[cite: 3]
* Tasks are shown as boxes, arrows show dependencies.[cite: 3]
* There is both a start and end point to the project.[cite: 3]
* Using the previous tasks, the critical path identified is 55 days.[cite: 3]

### Example: Building a House

| Node | Task | Duration |
| :--- | :--- | :--- |
| **A**[cite: 3] | Excavate[cite: 3] | 5 days[cite: 3] |
| **B**[cite: 3] | Foundation[cite: 3] | 2 days[cite: 3] |
| **C**[cite: 3] | Frame[cite: 3] | 12 days[cite: 3] |
| **D**[cite: 3] | Electrical[cite: 3] | 9 days[cite: 3] |
| **E**[cite: 3] | Roof[cite: 3] | 5 days[cite: 3] |
| **F**[cite: 3] | Masonry[cite: 3] | 8 days[cite: 3] |
| **G**[cite: 3] | Interior[cite: 3] | 10 days[cite: 3] |
| **H**[cite: 3] | Exterior[cite: 3] | 7 days[cite: 3] |
| **I**[cite: 3] | Landscape[cite: 3] | 5 days[cite: 3] |

**Process Flow and Critical Path Analysis:**
* Steps A, B, and C run in series. Step B cannot happen until A is completed; step C cannot happen until B is completed.[cite: 3]
* Steps D, E, and F run in parallel.[cite: 3]
* Step H cannot happen until steps D, E, and F have ALL been completed.[cite: 3] This is important because parallel steps will likely have different expected completion times.[cite: 3]
* **Critical Path Definition:** A line that goes through all of the nodes that have the longest expected completion times.[cite: 3]
* It represents the shortest time in which a project can be completed.[cite: 3] Any activity on the critical path that is delayed delays the entire project.[cite: 3]
* Nodes not on the critical path can be delayed for some amount of time without delaying the final completion of the project.[cite: 3]
* For the house example, among parallel nodes D, E, and F, node D is expected to take the longest. The critical path runs through D and G because they have the longest expected completion times.[cite: 3]
* The final sequence on the critical path is: START -> A -> B -> C -> D -> G -> H -> I -> END.[cite: 3]

### Time Estimations
* **Most Likely Time (Real Time):** The expected completion time as defined by the critical path.[cite: 3]
  * $5 + 2 + 12 + 9 + 10 + 7 + 5 = 50$ days.[cite: 3]
* **Optimistic Time:** The best case time. Determined by deciding upon the shortest possible time for each node on the critical path and adding them up.[cite: 3]
  * $4 + 2 + 10 + 8 + 8 + 7 + 4 = 43$ days.[cite: 3]
* **Pessimistic Time:** The worst case time. Determined by deciding upon the longest possible time for each node on the critical path and adding them up.[cite: 3]
  * $7 + 3 + 14 + 10 + 11 + 8 + 6 = 59$ days.[cite: 3]

**Expected Time Calculation:**
* It means the project most likely will take 50 days, but it could take 59 days, or it can be done as soon as 43 days.[cite: 3]
* Formula: $$Expected Time = \frac{Optimistic + [4 \times (Most Likely)] + Pessimistic}{6}$$[cite: 3]
* Calculation: $$Expected Time = \frac{43 + 200 + 59}{6} = 50.3 days$$[cite: 3]
